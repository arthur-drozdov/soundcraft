## 1. Summary

- **The DAW is a SoundCraft fork ("Studio").** It runs on the laptop with its control channel open. The agent drives it through SoundCraft's existing MCP bridge, and you watch every edit happen in the open window.
- **Sound generation runs on the DGX Spark** as a separate HTTP service ("Forge"). Forge wraps Foundation-1/1.2, Stable Audio 3, ACE-Step 1.5, stem splitting and melody transcription. A thin MCP client on the laptop ("Forge MCP") submits jobs and downloads the results into a local inbox, which Studio then imports from.
- **Gary4juce is a reference, not a dependency.** No VST sits in the loop, and no AGPL code is copied into SoundCraft.
- **Plugin understanding comes from a "Plugin Atlas".** It combines three sources: the parameter metadata the host already reports (SoundCraft reads VST3 titles, units, ranges, step counts and the plugin's own value text), meanings taken from the plugin manuals, and measured calibration.
- **The workflow is audio-first**: generate, chop, arrange, process. MIDI is used for playable parts: you sing, the agent transcribes, and the notes play on any instrument.
- **Most of the DAW side already exists.** The new Studio work is small and specific: a plugin-describe query, audio-to-MIDI straight into a clip, a multi-zone sampler with SFZ import, checkpoints, and visibility helpers. Most of the new work is in Forge, the Atlas and the playbooks.

## 2. Goals and non-goals

**Goals**

| # | Goal |
|---|---|
| G1 | The agent makes complex arrangement edits (split, chop, move, duplicate, repeat, trim, fade, gain) and checks each one. |
| G2 | The agent operates every host-exposed parameter of every loaded plugin, and can explain what a parameter does and why it changed it. |
| G3 | The agent generates its own material on the Spark: one-shots, loops, textures, FX, and playable instruments. |
| G4 | You sing or hum a melody, and the agent turns it into an editable MIDI part on an instrument you choose. |
| G5 | You see the agent's work live in the open DAW and can take over at any moment. |
| G6 | Every agent change can be undone and is checkpointed, and the agent reports exactly what it changed. |

**Non-goals**

- FL Studio integration, an FL clone, or reverse-engineering FL or any plugin (REA). Revisit only if a specific blocker appears that the fork can't solve.
- Whole-song generation in the style of Suno. The models supply ingredients; the agent composes.
- Hardware MIDI input, control surfaces, Pro Tools interchange and compressed export. SoundCraft gaps G-02, G-03, G-10 and G-21 stay open; this project doesn't need them.
- Commercial release of generated material, until the licence review in §6.7 is done.

## 3. Decisions

| # | Decision | Why | Revisit if |
|---|---|---|---|
| D1 | Fork SoundCraft as the DAW. | It is the only candidate that already combines a finished UI, a command model shared by UI/CLI/MCP, live MCP control, VST3/CLAP/AU hosting, and a permissive licence (MIT/Apache-2.0). | Phase 0 shows engine-level defects. Fall back to evaluating Tracktion Engine. |
| D2 | Generation is a service on the Spark; the DAW stays on the laptop. | Inference is asynchronous and GPU-bound; playback is real-time and local. | — |
| D3 | No Gary4juce at runtime. | The agent needs an API, not a GUI. Gary's model backends are separate services anyway. SoundCraft's rules forbid copying AGPL code into it. | You want a human-facing generation panel: use Gary's standalone app against Forge's Gary-compatible shim (§6.8). |
| D4 | The interactive session lives on the laptop. Headless SoundCraft on the Spark is only a later render worker. | Sessions don't replicate between instances, so a Spark-side edit would not appear in your window. | — |
| D5 | Audio-first; MIDI for playable parts. | Matches a sampling workflow. MIDI keeps melodies editable after the fact. | — |
| D6 | The agent edits through commands, not synthetic mouse input. | Commands are exact and verifiable. Synthetic input is reserved for plugin features that only exist in the plugin's own UI. | — |
| D7 | Built-in instruments and effects first. Third-party plugins are admitted to the agent's palette once profiled. | Plugins are hosted in-process, so a crashing plugin takes the whole session down (gap G-13). | Out-of-process hosting lands. |

## 4. Architecture

| Component | Runs on | Role | Status |
|---|---|---|---|
| **Studio**: this fork's desktop app, started with `--control <port>` | Laptop | The session, editing, instruments, plugins, mixing, rendering | Exists [V]; additions in §5.3 |
| **Studio MCP**: `soundcraft-cli mcp --connect <port>` | Laptop | Agent ↔ Studio: commands, inspection, screenshots, synthetic input | Exists [V] |
| **Forge** | Spark | Model inference, job queue, asset store, post-processing, analysis, transcription | New [P] |
| **Forge MCP** | Laptop | Agent ↔ Forge; downloads assets into the inbox | New [P] |
| **Plugin Atlas** | Laptop (git repo, plus MCP tools) | Plugin profiles and the profiler | New [P] |
| **Playbooks** | Your music project folder | Skills / CLAUDE.md for musical operations and the verify loop | New [P] |
| **Render worker**: headless `soundcraft-cli` | Spark | Batch variations and renders | Later [P] |

**Data flow**

1. The agent asks Forge MCP for material, and Forge queues a job on the Spark.
2. Forge MCP polls the job, then downloads the WAV and its metadata sidecar into the inbox on the laptop.
3. The agent imports the result into Studio (`file.import_audio`, `mix.sampler_load` or an SFZ import), then arranges, processes and automates it.
4. The agent bounces a preview range. `file.bounce_mix` takes `start`/`end`, and the MCP `bounce_mix` tool returns peak dBFS and integrated LUFS. Optionally it uploads the preview to Forge for analysis or transformation, then iterates.
5. You watch in the open Studio window. The agent can take `ui.screenshot` captures for its own visual checks.

**Network**

- Studio's control channel binds to `127.0.0.1` only [V `docs/control-protocol.md:29`], so the agent and Studio MCP run on the laptop.
- Forge listens on a private network only (Tailscale/WireGuard or an SSH tunnel), uses bearer-token auth, and is never exposed to the public internet.
- Large audio moves as files over HTTP: multipart upload and streamed download, not base64 inside JSON.

### 5.3 Additions [P]

Every addition follows `AGENTS.md`:
- it is a command with its own `specs()` module and tests;
- it obeys the never-crash rules (no panics, hostile-input handling, nothing blocking on the audio thread);
- `docs/control-protocol.md` / `docs/mcp.md` are updated;
- `cargo xtask ci` passes.

Fork-specific commands go in new modules so upstream merges stay clean. Generic ones (S1, S2, S4, S5) are offered upstream.

| # | Addition | Requirement |
|---|---|---|
| **S1** | `plugin.describe {track, slot \| instrument: true}` (query) | Returns identity (format, plugin id, name, vendor, version, category), and for every parameter: id, name, min, max, default, unit, taper, choices, current value and current value text. Also state size and whether an editor is available. Must work for built-in, VST3, CLAP and AU. **Check first** whether `track.inspect` or `session.inspect {detail:"full"}` already returns this; if so, extend that rather than add a command. |
| **S2** | `plugin.param_text {track, slot, param, values[]}` (query) | The plugin's own display text for each value given, without changing the session. Used for calibration (e.g. 0.37 → "2.4 kHz"). |
| **S3** | `midi.from_audio {track, start, end, to_track?, quantize?, min_note_ms?, key_snap?}` | Runs the existing monophonic tracker and writes the result straight into a new MIDI clip (on a new or given instrument track). Returns the notes with per-note confidence. One undo step. |
| **S4** | Multi-zone sampler ("Keybed") | Extend the built-in sampler, or add a built-in `keybed` instrument, holding N zones: sample, root note, key range, velocity range, tune, gain, loop points; ADSR and filter are shared. Commands: `mix.sampler_zones_set {track, zones[]}` and `file.import_sfz {path, track?}`. SFZ subset: `<region>` with `sample`, `pitch_keycenter`, `lokey/hikey`, `lovel/hivel`, `tune`, `volume`, `loop_mode/start/end`, `ampeg_*`. Optionally, DecentSampler `.dspreset` import. Zone audio is saved in `Audio Files/` like sampler audio. The parser is our own implementation (clean-room rules). |
| **S5** | `audio.analyze {clip \| track+start+end}` (query) | Returns peak, RMS, integrated LUFS, duration, onset times, estimated BPM and key with confidence, and spectral centroid. Lets the agent verify material and previews even when the Spark is offline. |
| **S6** | Agent visibility | `ui.reveal {track?, start, end}` scrolls and zooms the Edit window to the region being edited. A status-line entry shows the last agent command's label. Reuse existing view commands where they already do this. |
| **S7** | `session.checkpoint {label}` and `session.checkpoints` | Saves a copy to `Checkpoints/<timestamp>-<label>.scraft` beside the session (wrapping `session.save_copy`) and returns its path; `session.checkpoints` lists them. |
| **S8** | macOS entitlement | Only if the laptop is a Mac: sign the fork's build with `com.apple.security.cs.disable-library-validation` (G-05). |

**Stopgap until S4 lands:** a Forge keybed can be played by loading its SFZ into a free SFZ player plugin by hand. The agent can't load a file into a third-party plugin through parameters, so it can't do this step itself.

## 6. Forge: the generation service on the DGX Spark [P]

### 6.1 Responsibilities

Forge hosts the models and runs the job queue, the asset store, post-processing, analysis and transcription. It never touches DAW sessions; it only produces and analyses files.

### 6.2 Models

All model facts in this table are [R] until Phase 0/1 confirms them on the Spark.

| Family | Model | Used for | Notes |
|---|---|---|---|
| loop | Foundation-1 (RoyalCities) | Tempo- and key-aware 4/8-bar instrumental loops | Trained at 100, 110, 120, 128, 130, 140 and 150 BPM. No drums. Stability AI Community Licence. |
| sample | Foundation-1.2 Samples | Pitched one-shots and short musical material | Same licence |
| instrument | Foundation-1.2 Keybeds, via the RC Stable Audio Tools pipeline | A set of samples across pitches (shared seed, pitch conditioning, slicing, mapping), exported as a playable instrument (SFZ / DecentSampler) | Author's figures: about 7 GB VRAM, about 50 s per single-layer keybed on an RTX 3090. Consistency across pitches is not guaranteed. |
| sfx / percussion / texture | Stable Audio 3 Small-SFX, Medium | Impacts, risers, atmospheres, percussion | Supports audio-to-audio, inpainting, continuation and LoRA. Community Licence. |
| music / transform | Stable Audio 3 Small-Music, Medium | Phrases, loop variations, transformations of existing audio | Same as above |
| layer / vocal | ACE-Step 1.5 (base / XL-base) | Complementary layers, vocals, extract/complete | MIT. Minimum about 10 s. Lego/extract/complete exist only on the base variants. |
| stems | stems.cpp (MIT runtime), or ACE-Step extract | Splitting generated material into parts | Some stem models are unlicensed or GPL; use only licensed ones. |
| transcribe | Spotify Basic Pitch | Voice → MIDI with pitch bends | Apache-2.0. Best on one instrument at a time. |
| analyze | Permissively licensed analysis libraries | BPM, key, onsets, loudness, loop seam | — |

**Admission rule:** a model joins Forge only after it (a) runs on the Spark (ARM64 + CUDA), and (b) passes a 10-prompt listening check by you.

**Excluded:** non-commercial weights (MusicGen, MelodyFlow, TangoFlux). Revisit only for a personal-only setup.

### 6.3 HTTP API

The API is versioned under `/v1`, uses JSON bodies, and requires a bearer token.

| Method and path | Purpose | Key fields |
|---|---|---|
| GET `/v1/health` | Liveness and GPU state | status, GPU memory used/free, loaded models |
| GET `/v1/models` | What can run | per model: id, family, checkpoint hash, licence, loaded/warm, VRAM, job types, parameter schema |
| POST `/v1/models/{id}/load`, `/unload` | Warm or free a model | — |
| POST `/v1/uploads` | Upload input audio (multipart) | returns `asset_id` |
| POST `/v1/jobs` | Submit work | `type`, `model?`, `params`, `candidates` (1–8), `priority?`, `idempotency_key?`; returns `job_id` |
| GET `/v1/jobs/{id}` | Job state | `state` (queued, running, succeeded, failed, cancelled), queue position, `progress` 0–1, ETA, error, result `asset_ids` |
| DELETE `/v1/jobs/{id}` | Cancel a job | — |
| GET `/v1/events` | Optional server-sent events, instead of polling | job progress and completion |
| GET `/v1/assets/{id}` | Download the result | WAV, MIDI, or a zip bundle for instruments |
| GET `/v1/assets/{id}/meta` | Metadata sidecar | see §6.5 |
| GET `/v1/assets?…` | Search earlier results | tags, prompt text, job, date, rating |
| POST `/v1/assets/{id}/rate` | Record your verdict | rating, note; informs later prompt choices |

### 6.4 Job types

**Common parameters:**
- `prompt` (free text) and structured `tags` (family, subfamily, timbre descriptors, effects; Foundation's tag vocabulary where it applies);
- `seed` and `candidates`;
- `duration_s` or `bars`; `bpm`; `key` (root and mode);
- output `sample_rate` (default 48 kHz to match the session; Forge resamples) and `channels`;
- `post` options: trim silence, fade length, normalise (peak −1 dBFS, or a LUFS target), loop crossfade.

| Type | Specific inputs | Output | Model |
|---|---|---|---|
| `generate.loop` | bars (4\|8), bpm, key, tags | WAV per candidate | Foundation-1, or SA3 |
| `generate.sample` | MIDI note, length, tags | WAV | Foundation-1.2 Samples |
| `generate.instrument` | note range, step (e.g. every 3 semitones), velocity layers (1–3), tags, shared seed | Zone WAVs + SFZ + DecentSampler file + zone manifest | Foundation-1.2 Keybeds |
| `generate.sfx` | duration, tags | WAV | SA3 Small-SFX / Medium |
| `transform.audio` | input asset, strength, prompt | WAV | SA3 audio-to-audio, or Foundation audio2audio |
| `extend.audio` | input asset, seconds | WAV | SA3 continuation |
| `inpaint.audio` | input asset, region, prompt | WAV | SA3 |
| `layer.add` | input asset, layer description | WAV | ACE-Step Lego |
| `stems.split` | input asset, stem model | WAV per stem | stems.cpp / ACE-Step extract |
| `transcribe.melody` | input asset, monophonic hint | MIDI file + note list | Basic Pitch |
| `analyze.audio` | input asset | BPM, key, onsets, LUFS, peak, duration, loop seam score | analysis libraries |

### 6.5 Post-processing and metadata

Every output goes through the same pipeline:
1. Decode, then trim if requested, apply fades, and normalise loudness or peak.
2. Measure: duration, peak, LUFS, BPM, key, onset count, clipping, DC offset.
3. Write the WAV (24-bit or 32-bit float) plus a JSON sidecar.

**Sidecar fields:**
- identity: `asset_id` (content hash), `job_id`, `type`, model id, checkpoint hash, model licence;
- request: prompt, tags, seed, all params;
- requested BPM/key next to measured BPM/key (with confidence);
- audio: duration, sample rate, channels, peak, LUFS;
- `parents` (the asset ids it came from), `created_at`, `rating`.

**Rule:** when the requested and measured values differ, Forge reports both. It never silently assumes the requested value.

### 6.6 Runtime and operations

- **Workers:** one worker process per model family, each with its own Python environment (their dependency pins conflict). A gateway runs a single GPU queue, FIFO with priority so previews go before batches. Start with one concurrent job per heavy model.
- **Memory:** warm models on demand and unload the least recently used one when memory runs short. The Spark's memory is unified, so set a budget that leaves headroom for the OS and the future render worker.
- **Packaging:** containers on an ARM64 CUDA base image (e.g. NGC PyTorch), or virtual environments; systemd units, plus a compose file for the whole bundle.
- **Storage:** `assets/<yyyy>/<mm>/<asset_id>.*`. Rated or used assets are kept; unrated ones are purged after N days.
- **Observability:** structured per-job logs, timings and GPU memory; `/v1/health` for the agent.
- **Security:** bound to the private interface only, with the token in the environment. Uploads are size- and duration-capped, and every input is treated as hostile (format checks).
- **Porting risk:** the Spark pairs an ARM64 CPU with a Blackwell GPU. Some wheels (torchaudio, attention kernels) may need source builds. Follow NVIDIA's DGX Spark porting guide and validate each model on its own in Phase 0. Gary's developer runs their remote backend on a DGX Spark [R `gary4juce/README.md:163`]: a precedent, not proof that every model works.

### 6.7 Implementation sources and licence hygiene

- **Build against the upstream model repos:** Stability `stable-audio-3`, RoyalCities' RC Stable Audio Tools, ACE-Step 1.5, Basic Pitch, and stems.cpp.
- **Use Gary4juce's client→backend contract as a behavioural reference** for which fields and defaults each model needs [V `gary4juce`]:
  - one localhost port per service: Gary 8000, Terry/MelodyFlow 8002, Carey/ACE-Step 8003, Jerry 8005, SA3 8006, YuE 8007, Foundation 8015 (`Source/PluginProcessor.cpp:285-323`);
  - a job is a POST of JSON, answered with `{success, session_id}`, then polled with GET `/poll_status/{session_id}` (Foundation, SA3, Carey, YuE) or `/api/juce/poll_status/{session_id}` (Gary, Terry) (`Source/PluginEditor.cpp:3106-3123`); the poll reply carries `progress`, `queue_status` and, when done, base64 `audio_data` (e.g. `Source/PluginEditor.Carey.cpp:1005-1024`);
  - the Foundation request carries `seed`, `bars`, `host_bpm`, `key_root`/`key_mode`, `family`/`subfamily`, descriptor fields, effect toggles and amounts, `behavior_tags`, `guidance_scale` and `steps`; audio-to-audio adds base64 `audio_data` and `init_noise_level` (`Source/PluginEditor.Foundation.cpp:84-186`).
- **Gary4juce is AGPL-3.0-only**, and its companion services carry their own licences. Copying its code makes Forge AGPL. That's acceptable for personal use, but the network-use clause applies if anyone else uses the service. **Never copy Gary code into SoundCraft**: its AGENTS.md forbids GPL/AGPL code.
- **Check RC Stable Audio Tools' own code licence** before vendoring its keybed pipeline.
- **Stability Community Licence:** commercial use carries conditions, including registration and an annual-revenue threshold. Read the exact terms before any release.

### 6.8 Optional: a Gary-compatible shim

Forge could also expose Gary's endpoint shapes (`/generate`, `/poll_status/{id}` and so on, on the same per-service ports). Gary's standalone app in localhost mode, with an SSH tunnel from the laptop's ports to the Spark, could then use Forge for hands-on exploration. This is a nice-to-have and not on the critical path.

## 7. Forge MCP (on the laptop) [P]

| Tool | Behaviour |
|---|---|
| `forge_models` | Lists models and their status. |
| `forge_submit {type, params, candidates, wait_s?}` | Submits a job and returns `job_id`. If the job finishes within `wait_s`, it also returns the results. |
| `forge_job {job_id}` | State and progress. |
| `forge_cancel {job_id}` | Cancels a job. |
| `forge_fetch {asset_id}` | Downloads into the inbox and returns local absolute path(s) plus a sidecar summary. |
| `forge_upload {path}` | Uploads a local file (it must be inside the project folder) and returns an `asset_id`. |
| `forge_search {tags?, text?, rated?}` | Finds earlier assets, so they are reused before anything is regenerated. |
| `forge_rate {asset_id, rating, note}` | Stores your verdict. |

- **Inbox:** `<project>/Forge Inbox/<date>/<asset_id>.wav` plus `.json`. Instruments land as a folder holding the zones and the `.sfz`. Forge MCP writes nowhere else.
- **Resilience:** retries with backoff and resumable downloads. If Forge is offline, it says so clearly, and the agent carries on with the assets it already has.
- **Implementation:** the official Python or TypeScript MCP SDK over stdio. The Forge URL and token come from the environment.

## 8. Plugin Atlas [P]

### 8.1 What a profile contains

There is one YAML file per plugin per major version, keyed by format, plugin id and version.

- **Identity:** name, vendor, format, plugin id (e.g. `vst3:<hex>`), version, OS, profile date.
- **Each parameter:**
  - host id and host name;
  - semantic name, section and role (e.g. "filter cutoff");
  - unit, range and taper, plus value-text calibration points and the default;
  - what it does (one line) and its musical use;
  - interactions (e.g. "only active when Filter Enable is on");
  - the safe range for agent changes, and whether it can be automated.
- **Signal flow and modes:** a short summary.
- **UI-only features:** controls that are not host parameters, each with a tested synthetic-input procedure or marked "manual only".
- **Presets:** names, and how to load them (state blob through `mix.insert_state`, or the UI).
- **Known issues:** crashes, latency, state-recall bugs.
- **Provenance on every field:** host, manual (with section/page), measured, or inferred, plus a confidence. An inferred value is never presented as fact.

### 8.2 Profiler workflow

1. In a scratch session, insert the plugin and read its raw table with S1.
2. Calibrate each continuous parameter with S2 at 11–21 points, and derive its units and taper.
3. Measure behaviour by offline-bouncing a test signal at low, mid and high settings of each parameter. Effects get noise, a sine sweep and a drum loop; instruments get a sustained chord. Analyse level, spectral centroid, bandwidth and envelope. This also flags parameters that do nothing in the current mode. All of this is offline: never sweep parameters during live playback.
4. Ingest the manual: you supply the PDF, the agent extracts the meaning of each control and links it to the manual section.
5. The agent writes a draft profile, you review it, and it's committed.
6. Re-profile whenever S1 reports a version different from the profile's.

### 8.3 Rules for the agent

- Load the profile before touching a plugin. With no profile, the agent only reads the plugin's values, or uses a built-in instead.
- Explain changes in plain terms, with display values before and after (e.g. "Cutoff 1.2 kHz → 2.4 kHz: brighter attack").
- Batch related changes, then verify by reading the values back and bouncing a short preview.

### 8.4 Scope

Start with SoundCraft's built-ins (their metadata is complete) and your top 5–10 third-party plugins.

## 9. Workflows (agent playbooks) [P]

The playbooks are stored as skills / CLAUDE.md in your music project folder.

### 9.1 The verified edit loop (used by every playbook)

1. Inspect (`session.inspect` summary) and state the intent.
2. Checkpoint (S7) before any batch longer than a few commands.
3. Run the change as one `batch`.
4. Re-inspect the affected tracks and clips, and compare them to the intent.
5. Bounce the affected range and check peak and LUFS; analyse it if useful.
6. Report what changed: tracks, clips, positions, and parameters old → new; the undo/checkpoint pointer; the preview file.

### 9.2 Sample-first composition

1. Generate candidates.
2. Audition them: you listen, and the agent reads the analysis.
3. Import the chosen ones.
4. Chop them (`edit.separate_at_transients` / `edit.separate_on_grid`).
5. Resequence (`edit.move_clips`, `edit.duplicate`, `edit.repeat`).
6. Process (inserts, clip gain, fades) and automate.
7. Bounce a preview.

### 9.3 Playable sample instruments

- **Single sample:** `generate.sample`, then `mix.sampler_load` with the root note taken from the sidecar.
- **Multi-sample:** `generate.instrument`, then S4 (`file.import_sfz`).

### 9.4 Sing → MIDI → instrument

1. Record a short take in the desktop app, or import a voice memo.
2. Transcribe with S3 `midi.from_audio`. If its accuracy is poor, fall back to Forge `transcribe.melody`, then `file.import_midi`.
3. Clean up: drop notes shorter than N ms, merge glides, snap to key, and quantise at ≤ 50 % strength unless asked otherwise.
4. Keep the original vocal muted on a reference track.
5. Assign an instrument (built-in synth, VST3, sampler or keybed) and audition alternatives.

### 9.5 Section operations

- Duplicate a section; make the second chorus bigger (layer with `layer.add` or a sample).
- Build transitions: a riser from `generate.sfx`, filter-sweep automation, a reverse through `audiosuite.process`, a drum cut on the last beat.

### 9.6 Session conventions

- One marker per section (intro, verse, chorus, drop).
- Track names prefixed by role (DRM, BAS, SYN, FX, VOX) and colours by role; tracks the agent creates are tagged.
- The template has a limiter on the master; previews never exceed −1 dBFS peak.
